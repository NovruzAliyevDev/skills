## Progress line contract

Ticket 01 starts it, and each later ticket adds the wording of the lines it writes. The server parses what is written here.

Every line starts with the timestamp and two spaces, as before. Admin lines record what the user asked and what was applied; they start with `admin: `. The server ignores them when it judges a run's progress: a run whose log holds only admin lines has not started.

| Line | Written by | Written when |
|---|---|---|
| `admin: pause requested` | server | Pause was applied: `pause` is set in `control.json`. |
| `admin: pause cancelled` | server | Cancel pause was applied: `pause` is cleared. |
| `admin: continue - run.ps1 launched in a new window` | server | Continue was applied: `pause` is cleared if it was set, then the run folder's `run.ps1` is opened as the skill opens it. The runner's `Queue` line follows. |
| `admin: skip requested (task <id>)` | server | Skip was applied: the task id is added to `skip` in `control.json`. |
| `admin: unskip requested (task <id>)` | server | Un-skip was applied: the task id is removed from `skip`. |
| `admin: <action> refused (<reason>)` | server | An action the run's state does not allow (the request answered 409). `<action>` is `stop`, `pause`, `cancel-pause`, `continue`, `skip`, `unskip`, `retry` or `edit-brief`. The reasons: `the run is finished`, `no runner of this run is alive`, `the process check is still pending`, `a pause is already asked for`, `no pause is asked for`, `a runner of this run is alive`, `the runner is starting`. A task action's reason starts with `task <id>: `, then one of `the run is finished`, `the task is skipped: it has its SKIPPED report`, `the task is not marked to be skipped`, `the task is already marked to be skipped`, `the task has started`, `the task's group has started`, and for retry `the task has not failed or stopped`, `the task has no session to resume`, or one of the run reasons `the process check is still pending`, `the runner is starting`, `a runner of this run is alive`. Requests answered 400, 403, 404 or 413 leave no line. Neither do requests for a run folder without the feature marker: the server does not write into run folders it cannot administer, although user story 49 asks for a line for every refusal. |
| `admin: stop requested - the runner (process <pid>) and its sessions were killed` | server | Stop was applied: the runner the lock names, its `-ParallelTask` children, their sessions and every process under them are killed. The lines below follow, in this order, then `Queue - STOPPED (by the user)`. |
| `admin: stop - task <id> cut off, to resume on Continue (session <session id>, entry <entry id>)` | server | A task running when Stop came (running or no-session) whose current attempt has a session: the session its last `starting` line started (or resumed), never an earlier attempt's. The server wrote its `resume` entry. One line per task. |
| `admin: stop - task <id> cut off, with no session to resume` | server | Such a task without a session id yet: Continue starts it over, as a re-run does. |
| `admin: stop - conflict session of group <group> cut off; Continue tries the merge again` | server | A conflict session was running when Stop came. It is not resumed: Continue starts the merge step again, with a new conflict session at its first conflict. |
| `admin: stop - merge undone (git merge --abort)` | server | A group's merge step had a merge in progress in the main checkout: the server aborted it and, if anything was left uncommitted or untracked there, reset the checkout to its commit and removed the untracked files, as the runner undoes a failed merge. |
| `admin: stop - the merge could not be undone (<git's last line>)` | server | The same, when git failed. The checkout needs the user's hand before Continue. |
| `admin: stop incomplete (<why>)` | server | Some processes of the queue were still alive after the kill (`processes <pids> of the queue are still alive`), or the process table could not be read. No `STOPPED` line and no `resume` entries follow; the request answers 500. |
| `Queue - STOPPED (by the user)` | server | The last line of a hard stop. The run state is `stopped`; each task and conflict session that was running is `stopped`, with the reason `stopped by the user from the monitor`, and a merge step in progress is `failed` with that reason. |
| `admin: resume applied (task <id>, entry <entry id>)` | runner | The runner reached a task with an unused `resume` entry and resumes its session: this line, then the task's `starting` line, and no `session` line (the session id is the same). The resume message says that the user stopped the queue and asks the session to check the working tree, carry on and write its report; the no-report rule applies. A parallel task is resumed in its worktree. The runner window prints it in yellow. An entry is used once this line names its id; the server drops used entries when it writes the next stop's. |
| `admin: brief edited (task <id>)` | server | Edit brief was applied: the brief `tasks\<id>.md` was replaced whole by the text the user saved, as typed. |
| `admin: retry requested (task <id>, mode <mode>, entry <entry id>)` | server | Retry was applied: the task's `retry` entry is written (`<mode>` is `resume` or `fresh`; the entry id is 12 hex digits), a `resume` entry a stop left for the task is dropped, `pause` is cleared, and the run folder's `run.ps1` is opened as Continue opens it. With a note, the line goes on with ` - note: <the note on one line>`. A fresh retry with a note first appended the note to the brief `tasks\<id>.md`, which is written whole: a blank line, `## Note from the user for a retry (<time>)`, a blank line, the note. |
| `admin: retry applied (task <id>, mode <mode>, entry <entry id>)` | runner | The runner reached a task with an unused `retry` entry: this line, then the task's `starting` line. `resume`: the task's last session is resumed (no `session` line follows), with a message saying the earlier attempt did not finish, naming its report (`results\<id>.previous.md`, or saying it wrote none), carrying the user's note, and asking the session to check the working tree and carry on; the no-report rule applies. `fresh`: a new session starts, as a re-run does. A parallel task is retried in its worktree, and its group is merged after. A `retry` entry wins over a `resume` entry of the same task. The runner window prints it in yellow. An entry is used once this line names its id. |
| `admin: control.json ignored (<problem>)` | runner, server | The control file could not be read, so it means no commands. The problems: `it is not valid JSON`, `it is empty`, `version '<v>' is not one this runner knows` (`... this monitor knows` from the server). The runner writes it once until the problem changes; the server writes it with an admin action that reads it. |
| `admin: pause applied (<where>)` | runner | The runner found `pause` set at a read point and stops there. `<where>` is `at start` (right after the `Queue` line, before the preflight), `before task <id>`, `before group <first id>-<last id>`, or `after group <first id>-<last id>` (after its merge step). A pause asked during a group is applied only after its merge step. The runner window prints it in yellow. |
| `Queue - PAUSED (by the user)` | runner | Right after `admin: pause applied`. The runner then exits with code 0 and removes its lock. |
| `admin: skip applied (task <id>)` | runner | The runner reached a task listed in `skip` that is not DONE, and wrote its report `results\<id>.md`: `SKIPPED` on its first line, then a line saying the user skipped it from the monitor. A report already there is moved to `<id>.previous.md` first. The runner window prints it in yellow. |
| `[i/N] <title> - SKIPPED (by the user)` | runner | Right after `admin: skip applied`, in yellow. The task counts as finished from now on. |
| `[i/N] <title> - already SKIPPED, passed over` | runner | A re-run reaches a task whose report starts with `SKIPPED`, whether or not `skip` still lists it. |
| `Group <first id>-<last id> - passed over (all its tasks skipped)` | runner | Every task of a group not DONE was skipped at its start: no worktree, no merge step. |
| `Finished, <S> skipped: <D> of <N> tasks DONE. Reports: <folder>` | runner | The final line of a queue that finished with skipped tasks, in place of `All N tasks DONE. Reports: <folder>`. |

A pause asked while the last sequential task runs is never applied: the queue finishes, and its final line is the usual `All N tasks DONE`. A pause asked during a last group is applied after its merge step; Continue then only writes the final line.

The runner reads `control.json` before each sequential task that is not already DONE, before each group, and at start; never while a session runs. Its `version` is `1`. Tickets 01 to 03 use `pause`, `skip` (task ids as text) and `resume` (per task id, `{ session, id }`: the session to resume and the entry's id, 12 hex digits). Ticket 04 adds `retry` (per task id, `{ mode, id, note, session }`: `resume` or `fresh`, the entry's id, the user's note, empty when none, and for `resume` the task's last session id). The server drops used `retry` and `resume` entries when it writes a new one. The runner also reads `retry` and `resume` before each task's session starts, in the parallel children too.

**Skips and groups.** Skips of a group's tasks are read once, at the group's start, after the pause check before it: the tasks listed get their `SKIPPED` report and lines there. Two or more tasks left: the group runs with them only (its `starting` line lists them, and their sessions' prompts name only them). One left: that task runs as a sequential task in the main checkout, with no worktree, no branch and no merge step. None left: the `passed over` line. The group keeps its name `<first id>-<last id>` from `queue.json` either way, and the pause after the group is still checked. A re-run makes the same choice: the skipped tasks keep their `SKIPPED` report, and a group that started in an earlier run (one of its branches exists, or a task of it has a report other than `SKIPPED`) reads no skip entries again.

Before a sequential task, the skip is read before the pause: a task both skipped and paused before is skipped, and the pause applies at the next read point. A task the user marks between the runner's read of `control.json` and its `starting` line still runs; its entry stays in `skip` until un-skipped, and since it is no longer pending the page offers Un-skip for it only. The window is the moment between the read and the start, as for the brief edit of the spec.

**Run lock.** The runner writes its process id to `runner.lock` before its `Queue` line and removes the file when it exits, normally or by a stop or pause (not when it is killed). It creates the file only if it does not exist; it replaces a lock whose holder is gone, and goes on only if the file still names it a moment later. A runner that finds a lock naming a live PowerShell process running this run folder's `run.ps1` by its full path (not a `-ParallelTask` child) writes nothing to `progress.log`; its window shows, in red, `Another runner of this run folder is alive (process <pid>), so this one exits. Continue the queue from the monitor once that runner has stopped.`, and it exits with code 1. The `-ParallelTask` children neither check nor take the lock.

**Feature marker.** The runner carries the line `# task-queue control contract: 1`. The server offers admin actions only for run folders whose `run.ps1` carries it, and judges their runner by the lock: the runner is the process the lock names, so the window the skill opens (`-NoExit`) stops counting once its script has ended.

## Monitor: what ticket 01 added

- `GET /` carries `<meta name="admin-token" content="<token>">`, a random token made at each server start.
- `POST /api/admin` takes JSON `{ project, run, action }` with `action` one of `pause`, `cancel-pause`, `continue`. It needs the token in `X-Admin-Token` and an `Origin` of `http://127.0.0.1:<port>` or `http://localhost:<port>`; otherwise 403. Other methods there answer 405, as every non-GET request elsewhere. Answers: 200 `{ ok, action }`; 409 `{ error }` with the reason; 400 for a body that is not a JSON object, an unknown action or an invalid project or run name; 404 for an unknown run; 413 for a body over 1 MB. The server takes a fresh process snapshot before it judges an action. After a Continue, the new runner counts as alive (`the runner is starting`) until a process snapshot taken after the launch shows it, at most 30 s.
- `/api/run` answers `admin: { supported, actions }`: whether the run folder's runner copy has the marker, and the run-level actions allowed now. Run states gain `pausing` (pause asked, run running or no-session) and `paused` (after the `PAUSED` line, until the next `Queue` line). `paused` has a `finishedAt`, as the other stopped states.
- The page shows, under the run header of an unfinished run that supports admin actions, Pause (Cancel pause while one is asked) and Continue; an action not allowed now stays greyed and focusable. A refused action shows `<Action> refused: <reason>` beside them. The scene's sign reads PAUSED, the tab title starts with ⏸, and a notification says "Queue paused".

## Monitor: what ticket 02 added

- `POST /api/admin` takes task actions `{ project, run, action, task }` with `action` `skip` or `unskip`; a missing, invalid or unknown `task` answers 400. Skip is allowed for a pending task that is not marked yet, in no group that has started (a group has started once the runner wrote a line of it, or one of its tasks left `pending`), of a run not finished; un-skip for a task marked in `skip` that is not `skipped` yet. The runner need not be alive for either.
- `/api/run`: every task gains `skipPending` (pending and listed in `skip`) and `actions` (the task actions allowed now; empty for a run folder without the marker), and the state `skipped` (from its `SKIPPED` or `already SKIPPED` line). The run state `finished-with-skips` comes from the `Finished, ...` line; it is finished, as `done` is, so it has a `finishedAt` and no controls. A group left with fewer than two tasks by skips has the merge state `skipped`, and the task left in it is judged as a sequential task (its session belongs to the runner itself) and answers `group: null`, so the page shows it without its group's marks. `/api/runs` counts `skipped` tasks in `counts`.
- The page: the task drawer shows the task's allowed actions under its facts, Skip and Un-skip in one slot. Skip asks for confirmation in a dialog (Cancel has the focus; Esc closes only the dialog); Un-skip acts at once. A refusal shows `<Action> refused: <reason>` beside the button. A task marked to be skipped says so in the drawer and the tooltip, its worker is greyed in the queue line, and its name tag is dashed and grey. A skipped task has no figure: its desk stands grey and empty, with its name tag, in rows under the queue line, and the desk is its button. The run's badge, the run list and the scene's sign read `finished, N skipped`; the tab title starts with ✓, and the notification says `Queue finished, N skipped: D of T tasks DONE`.

## Monitor: what ticket 03 added

- `POST /api/admin` takes `stop`. It is allowed while the run is not finished and its runner is in the process table (refused with `the runner is starting` until a Continue's runner shows there). The answer comes once the processes are dead and the lines written, a few seconds: the server reads the whole process table (with creation times, since Windows reuses process ids) to find every process under the runner, kills them, and reads it again to make sure. It answers 500 with `admin: stop incomplete` when something survives, and 409 with `admin: stop refused (no runner of this run is alive)` when the runner ended by itself before the kill.
- The admin requests of one run folder are handled one at a time, so no action judges the run or writes `control.json` while a Stop is under way: a second Stop sent with the first finds no runner and is refused.
- A Continue's runner also stops counting as starting once its `Queue` line is in the log after the launch, so a runner killed before a process snapshot saw it does not hold Continue back for 30 s.
- `/api/run`: `admin.actions` can hold `stop`. The page shows Stop first in the header, red; it asks for confirmation in the dialog (Cancel has the focus; Esc closes only the dialog). A stopped task stands in the alert corner with the red mark, as a stopped task did before; no new sprites.

## Monitor: what ticket 04 added

- `POST /api/admin` takes `retry` with `{ project, run, action: 'retry', task, mode, note }`: `mode` is `resume` or `fresh` (anything else answers 400), `note` is optional text of at most 4000 characters (anything else answers 400; it is trimmed). Retry is allowed for a `failed` or `stopped` task of a run not finished, when no runner of the run is alive or starting and the process check is in, as for Continue; resume mode also needs a session of the task's last attempt (the one its last `starting` line started or resumed): a task whose last attempt died before naming a session can only start over, even when an earlier attempt had one. No confirmation is asked.
- `/api/run`: a task's `actions` can hold `retry`, and every task gains `retryModes`: the retry modes allowed now (`resume` and `fresh`, `fresh` only, or none). The page offers exactly those.
- A task resumed by a retry keeps its session: the hard stop's `admin: stop - task <id> cut off` line names that session, as for a task resumed after a stop.
- The page: the drawer's Retry button (`aria-expanded`) opens a form under the task's actions: the mode as two radio buttons (resume left out when `retryModes` lacks it; it is the first choice otherwise), a note field and a hint saying where the note goes, then Retry task and Cancel. Esc in the form closes only the form, and the focus goes back to Retry; while the request is on its way, Esc and Cancel wait for its answer. Sent, the form closes; refused, it shows `Retry refused: <reason>` and keeps the mode and the note. The Brief tab, when shown, loads the brief again after a retry.

## Monitor: what ticket 05 added

- `POST /api/admin` takes `edit-brief` with `{ project, run, action: 'edit-brief', task, brief }`: `brief` is the whole new text, stored exactly as sent (a `brief` that is not text, or only white space, answers 400; the 1 MB body limit bounds it). Edit brief is allowed, as Skip is, for a pending task in no group that has started, of a run not finished, also while the runner is alive; a task marked to be skipped can still be edited. The server writes the brief whole (a temporary file beside it, then a rename) and its admin line. No confirmation is asked. The runner reads the brief only when the task's session starts, so the next session sees the new text; a start between the server's check and its write misses the edit (spec, Further Notes).
- `/api/run`: a task's `actions` can hold `edit-brief`.
- The page: the drawer's Edit brief button, and an Edit button at the top of the Brief tab, open the Brief tab as a text box holding the brief as it is now, with Save and Cancel; both have `aria-expanded` and the focus goes to the text. Esc in the editor closes only the editor, and the focus goes back to Edit; while a save is on its way, Esc and Cancel wait for its answer. Saved, the editor closes and the tab shows the new brief, rendered as before (raw HTML as text, `javascript:` links going nowhere). The editor stays open while the task starts meanwhile, and its save is then refused with `Edit brief refused: <reason>`, the text kept.

## Check tooling

The checks of this spec run against the tooling of the earlier specs in `%TEMP%\task-queue-monitor-fixtures` (see the parallel-tasks README). Ticket 01 added:

- `check-admin.mjs`: `node check-admin.mjs [scenario...]` starts a monitor on port 4849 over `admin-root\` with the stub `claude` first in `PATH`, and plays `security`, `pause`, `cancel-pause`, `group`, `lock`, `old` and `unreadable` with the real runner: requests in, then `/api/run`, `progress.log`, the stub's calls, the lock file and the repository. Continue opens real runner windows; the check closes them at the end. About four minutes.
- `setup-admin-ui.mjs`: run folders under `admin-root\AdminUI` for checking the page's controls by hand in the browser pane (a monitor on port 4850 over `admin-root`, with the stub first in `PATH`).
- The stub `claude` learned `hold:<file>` (stay working until `<file>` appears beside the plan), and finds a run folder's `plan.json` by itself when no `STUB_PLAN` is set, as for a runner the monitor launched.
- `check-parallel.mjs` expects the new `admin` field in every run answer.

Ticket 02 added the `skip` scenario (skip and un-skip of a pending task, refusals, the `SKIPPED` report, the final line, the run list, a re-run) and `skip-group` (a group left with one task, a group passed over, a group of three left with two, skip refused in a started group, a re-run of a started group that reads no skips) to `check-admin.mjs`, now about six minutes; the `skip` and `skipped` run folders to `setup-admin-ui.mjs`; and `skipPending` and `actions` to the task fields `check-parallel.mjs` expects.

Ticket 03 added the `stop` scenario (stop refused without a runner; stop of a sequential task: the process gone, the lines, the resume entry, the stale lock, Continue resuming the same session with the stopped-by-user message; a runner killed outright after that, and Continue starting a new session since the entry is used), `stop-group` (two Stops sent at once: one applied, one refused; a group of two with one task DONE: both worktrees and branches kept, only the other task resumed, in its worktree, then merged) and `stop-conflict` (the merge aborted and the main checkout clean, the merge tried again with a new conflict session) to `check-admin.mjs`, now about nine minutes; the `stop` run folder to `setup-admin-ui.mjs`. The check's HTTP client opens a new connection per request: a kept-alive one could be closed by the server's keep-alive timeout as it was reused, which showed as `socket hang up` after the stop's long request.

Ticket 04 added the `retry` scenario (retry refused for a running and for a pending task, a bad mode or note answering 400; a retry by resume with a note: the last session resumed, the message naming the earlier report and carrying the note, the brief untouched, the server's and the runner's lines; a plain Continue after it starting a new session, since the entry is used; a fresh retry with a note: the brief ending with the note under its heading, a new session; a fresh retry whose attempt died before naming a session: only `fresh` offered, resume refused although an earlier session is known) and `retry-group` (a failed parallel task resumed in its worktree with the note, the other task not run again, the group merged) to `check-admin.mjs`; the `retry` run folder to `setup-admin-ui.mjs`; and `retryModes` to the task fields `check-parallel.mjs` expects. The stub `claude` learned `crash`: as a plan entry's first action, the call ends with exit code 1 before any output, so the attempt has no session id.

Ticket 05 added the `edit-brief` scenario (an edit of a pending task read by its session; an edit of a running task refused, the file unchanged, the refusal's line; a brief that is missing, not text or blank answering 400; an edit of a task in a group not started stored exactly as typed, raw HTML and a `javascript:` link included, with no temporary file left and `/api/file` answering the new text; an edit of a task pending in a group that has started refused; a later task edited while the queue runs, its session reading the new brief; a finished run refusing) to `check-admin.mjs`, and the `brief` run folder to `setup-admin-ui.mjs`. The `skip` scenario expects `edit-brief` beside `skip` and `unskip`. The stub `claude` records `brief`: the text of the brief its prompt names, as the session would read it at its start.
